T2 evidence summary: severity ladder, probe trajectories, and run provenance
============================================================================

All runs: Qwen2.5-1.5B-Instruct, GRPO (verl, FSDP2 + async colocated vLLM
0.11), Countdown-Tasks-3to4 (32,768 train / 1,024 test), 70 optimization
steps, batch 64 prompts x 8 samples, lr 2e-6, H100. The only intended
difference across arms is trainer.rollout_sync_interval (k). The probe column
is training/rollout_probs_diff_mean: mean per-token |log q - log p| between
the rollout engine's own logprobs (calculate_log_probs=True) and the trainer's
recomputed old_log_probs -- i.e. the sampler-trainer mismatch. The
engine-vs-trainer numerical noise floor with a fresh sync is ~0.001-0.005.

Run provenance (memory-tight colocated configuration)
------------------------------------------------------
The defective arms (k=64, both seeds) ran with the canonical configuration
exactly as shipped in workspace/run_grpo_stale_sync.sh. The control and
ladder arms recorded for this table needed run-time microbatch-packing
reductions to avoid CUDA OOM in this colocated setup (vLLM pool 0.25-0.30 vs
0.35, log_prob_max_token_len_per_gpu 12288 vs 24576, and for k=8 also
ppo_max_token_len_per_gpu 8192 vs 12288). These knobs only change how tokens
are split into microbatches (the weighted-mean gradient is unchanged); they
do not change the training objective or the failure mechanism, and the k=1
results match the recorded canonical-config debug run.
