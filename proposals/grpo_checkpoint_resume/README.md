# Task idea — GRPO resume advances the data cursor with a weights-only checkpoint

A robotics GRPO job using a project-specific Miles/Megatron launcher wrote policy weights and a ledger of committed rollout groups. Its checkpoint at iteration 14 contained policy shards and a recorded iteration. The ledger referenced that saved checkpoint index. The launcher had disabled both saving and loading optimizer and RNG state. Inspection of the actual distributed checkpoint index and its decoded common state found no Adam moments, learning-rate scheduler state or RNG snapshot. The available files support a warm start. Treating the iteration and ledger as a full resume silently changes the next optimizer update.

**Measured evidence.** The historical checkpoint index contained 50,410 entries. All four optimizer/RNG save and load suppression flags were enabled. To isolate the numerical effect, a separate CPU experiment used Megatron distributed checkpoint readers, its scheduler, and PyTorch AdamW. After three updates, a fresh process restored and performed update four. For both one and two ranks, a full restart matched the uninterrupted reference on all 11 checks, including the next loss, weights, optimizer moments, step, learning rate, scheduler clock and random draws. Omitting only the two Adam moments produced maximum absolute weight errors of 0.0182328820 and 0.0177786946, respectively. These measurements establish the continuation failure mode in the CPU test. The historical RL job establishes which checkpoint fields were present. The controlled numerical comparison comes from the CPU experiment.

**Proposed benchmark.** Stage a short real GRPO run using a small public policy and an offline-preparable dataset in an approved shared image. Save and restart at a fixed committed update. Run an uninterrupted control with the same seed, data order, worker layout and policy version. Record a fresh held-out evaluation, the first resumed group IDs, a digest of its actions and rewards, optimizer and scheduler clocks, and the first post-restart update. A separate replay of the exact same next rollout batch isolates optimizer continuity from RNG-driven rollout changes. The diagnosis must explain how a trainer can recover the same iteration, weights and data cursor while producing a different update. A repair must pair committed rollout progress with model, optimizer, scheduler and RNG state at the same update, maintain an explicit weights-only warm-start path, and select a complete pair after an interrupted write. A full task submission still requires the approved-image recording and startup check. Those recordings would provide the calibration data for any solution threshold.

An existing AutoRLBench checkpoint task diagnoses host-memory exhaustion during serialization. The run proposed here concerns missing state in a checkpoint that was written successfully.
