# Preparing an in-image RL recording

A suitable public experiment scaffold is the one-GPU Slime/Qwen3.5-0.8B recipe in AutoRLBench at commit `90ca620e0f648926ccd4b6680ad8fbcc72876816`. The launcher already uses both `--no-save-optim` and `--no-save-rng`. The original benchmark ran uninterrupted, a use in which a weights-only export can be intentional. A resume task needs a genuine cold restart with its original optimizer and group-progress contract. Use a healthy GRPO reward normalizer for both arms and replace the unrelated timeout injection with deterministic ordinary prompts. Preserve the public framework’s license, the license on the imported workspace, and all model source notices. [Recorded public launcher](https://github.com/Thinking-Space/AutoRLBench/blob/90ca620e0f648926ccd4b6680ad8fbcc72876816/tasks/algorithm/slime_excluded_rollout_grpo/workspace/run.sh) · [Pinned model preparation](https://github.com/Thinking-Space/AutoRLBench/blob/90ca620e0f648926ccd4b6680ad8fbcc72876816/tasks/algorithm/slime_excluded_rollout_grpo/environment/prepare.sh) · [Existing timeout oracle](https://github.com/Thinking-Space/AutoRLBench/blob/90ca620e0f648926ccd4b6680ad8fbcc72876816/tasks/algorithm/slime_excluded_rollout_grpo/evaluations/issue/oracle.md)

1. Pin the public source, policy, training examples, train/held-out split, dataset construction, hardware, RNG seeds and budget. Record a few complete online GRPO updates, with held-out evaluation and first nonzero optimizer moments. A warm-start mode deliberately discards optimizer history. Keep that mode separate from a declared full resume.
2. At a specified committed update A, record policy identity, the completed optimizer-step counter, LR clock, and the matching committed data cursor. Continue in the same process to A+1 as a numerical reference. Freeze sufficient rollout data at A+1 for deterministic replay. Also keep an online all-state restart comparison, where RNG restoration controls future rollouts.
3. Cold-start a new process at A. The defective and repaired workspaces differ only in recovery behavior. Quantify the first eligible update on the identical saved rollout using the same loss and reducer. Compare committed request and group IDs, per-batch reward and mask hashes, optimizer step, LR, moment norms, update magnitude and post-update model difference. Check a held-out evaluation in each arm. Separately capture independent runs on the same device topology to estimate baseline floating-point variation before selecting a tolerance.
4. Test the write boundary separately on the fixed path. Simulate a partially completed new save on an isolated working copy. Verify that the chosen step and data cursor both come from the previous complete pair; report statuses instead of classifying every incomplete historical save as a case of duplicated samples.
5. Keep the actual buggy and fixed run logs, per-step metrics, representative rollout records, configuration and code. If offline W&B is enabled, preserve the run history. Graders can reconstruct checkpoints inside `prepare.sh` or use a split run in the task to create them. Keep sensitive operational metadata, live-service endpoints, original model shards and training credentials out of release assets. Before PR, run the benchmark harness until the startup logs contain two distinct real training steps.

No official-image run has yet been recorded for this candidate. The proposed GPU count and model apply to the public scaffold. They do not retroactively describe the source robotics job.
